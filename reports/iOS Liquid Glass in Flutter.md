# Slip native glass under Hearthrise's ink

Hearthrise can use real Liquid Glass on iOS 26+ and keep its paper/ink design. The method is to host a **material-only native view** (a `UIVisualEffectView` with a `UIGlassEffect`, or SwiftUI `.glassEffect` in a `UIHostingController`) in a `UiKitView`. That view replaces only the bottom two layers of `GlassSurface`, the backdrop blur and the fill. The Flutter child and `GlassPainter`'s key line, rim and glint stay a normal Flutter subtree painted on top. Below iOS 26, the same widget falls back to today's `BackdropFilter` path unchanged. Every glass symbol is `@available(iOS 26.0)`, so the native code needs `#available` gating. A deployment target of iOS 15 builds fine against the 26/27 SDK. Flutter itself ships no Liquid Glass, native or drawn, as of October 2026. Its likely upstream direction is a shader imitation, not native wrapping. The native route has hard limits:
- Glass refracts only Flutter pixels painted *beneath* the platform view.
- A Flutter `BackdropFilter` in the same scene reportedly stops native glass from rendering at all.
- Every glass surface is a platform view with whole-screen compositing cost.
- An open engine bug causes jank whenever any platform view is on screen.

Treat native glass as a candidate for **two or three static chrome pieces per screen** (tab bar, header circles), not for sheets, list cards or anything that scrolls. Verify refraction of Flutter content on a real device before committing. Today the only evidence is a simulator report.

## Apple's API is small: one material, three variants, a container

SwiftUI exposes `glassEffect(_ glass: Glass = .regular, in shape: some Shape = DefaultGlassEffectShape())`. The default shape is a capsule, and any `Shape` is accepted, custom paths included ([Apple docs](https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:))). `Glass` has three variants (`.regular`, `.clear`, `.identity`) and two modifiers, `tint(_:)` and `interactive(_:)`. **The shipping SDK has no `isEnabled:` parameter.** Passing `.identity` is how you switch glass off without changing the view tree. That conclusion comes from the iPhoneOS 27.1 SDK's `SwiftUICore.swiftinterface`, which holds the same glass surface introduced in iOS 26 ([Apple: Applying Liquid Glass to custom views](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)). Four APIs handle grouping and motion:
- `GlassEffectContainer(spacing:)` groups effects so they render efficiently and blend together.
- `glassEffectID(_:in:)` morphs shapes across view-tree changes.
- `glassEffectUnion(id:namespace:)` merges distant shapes into one.
- `glassEffectTransition(.matchedGeometry | .materialize | .identity)` picks how glass appears and disappears.

Apple also says to apply `glassEffect` *after* other appearance modifiers ([Apple](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)).

UIKit is thinner. `UIGlassEffect(style: .regular | .clear)` is a `UIVisualEffect` with `tintColor` and `isInteractive`, and it has no identity style. `UIGlassContainerEffect` has a `spacing` property, "the distance between elements at which they begin to merge". The shape comes from the new `UIView.cornerConfiguration`, for example `.corners(radius: .fixed(16))`, `.capsule()` or `.containerConcentric()` ([WWDC25 284](https://developer.apple.com/videos/play/wwdc2025/284/)). WWDC snippets show `.fixed(8)` and `.containerRelative()` directly on `cornerConfiguration`; those are beta-era names that the shipping SDK replaced. **UIKit has no ID or union API, and its shape covers corners and capsules only.** That matters for Hearthrise, whose `GlassShape` offers circle, stadium and rounded rectangle. All three map onto `cornerConfiguration`. Custom paths, `glassEffectID` morphing and union need the SwiftUI path. To show glass, set `effectView.effect = glass` inside `UIView.animate`. To hide it, set `effect = nil`. Apple says "always prefer setting the effect property over the alpha" so the materialize animation plays ([WWDC25 284](https://developer.apple.com/videos/play/wwdc2025/284/)).

The material adapts on its own. Small elements flip between light and dark with the content behind them. Large ones grow more opaque but do not flip. A custom tint is remapped to "a range of tones that are mapped to content brightness underneath", so a tint never renders as an exact brand colour ([WWDC25 219](https://developer.apple.com/videos/play/wwdc2025/219/)). Clear "does not have adaptive behaviors" and needs a 35% dimming layer over bright content ([HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)). **Regular is the right variant for Hearthrise.**

## Availability is a compile-time gate with a moving SDK floor

All glass symbols carry `API_AVAILABLE(ios(26.0))` and are unavailable on visionOS. Using one outside `if #available(iOS 26, *)` is a compile error, not a runtime crash. That is standard weak linking, so an iOS 15 deployment target stays intact, and on iOS 15–18 the native side returns a `UIBlurEffect` or reports "unsupported" ([SDK header via Apple docs](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)). One trap concerns the opt-out key. `UIDesignRequiresCompatibility` opts an app out of the new system design, but "the system ignores this key when you build for iOS 27 or later" ([Apple docs](https://developer.apple.com/documentation/bundleresources/information-property-list/uidesignrequirescompatibility)). Apple DTS clarified that this means *linking against the iOS 27 SDK*. It does not mean the deployment target or the device OS ([Apple Developer Forums 832543](https://origin-devforums.apple.com/forums/thread/832543)). The Mac building Hearthrise already has Xcode 27.1, so the key is moot. That barely matters, because Flutter draws nearly all of Hearthrise's chrome. Only true system UI (keyboard, share sheet, alerts) changes.

The Dart side needs its own version check to decide which branch of `GlassSurface` to build. There are three options. You can parse `Platform.operatingSystemVersion` synchronously, which `cupertino_native_better` relies on and reports as working in release builds ([pub.dev](https://pub.dev/packages/cupertino_native_better)). You can read `device_info_plus`'s `iosInfo` asynchronously ([pub.dev docs](https://pub.dev/documentation/device_info_plus/latest/)). Or a one-line method channel can return whether `NSClassFromString("UIGlassEffect")` exists. The channel is the most honest gate, because it asks the OS for the capability rather than guessing from a version string. Resolve the answer once at startup and pass it down as a plain `bool`. Under the repo rule that `lib/ui/` widgets take values, not providers, `GlassSurface` takes something like `useNativeGlass: true`, and a widget test covers each branch.

## Four integration routes, and only one keeps the ink on top cleanly

| Route | Real Apple glass | Keeps hand-drawn overlay | Cost / risk |
|---|---|---|---|
| Material-only platform view under Flutter content (own plugin, or `real_liquid_glass`, `fresnel`) | Yes, iOS 26+ | Yes: overlay is ordinary Flutter on top | Platform-view compositing, BackdropFilter conflict, z-order bugs |
| Native control kits (`cupertino_native_better`, `adaptive_platform_ui`) | Yes, iOS 26+ | No: renders Apple's controls, not Hearthrise's | Two sources of truth for tab state, halo bleed over sheets |
| Shader imitation (`ImageFilter.shader`, `liquid_glass_renderer`, `liquid_glass_widgets`) | No | Yes | Impeller-only refraction, backdrop copies |
| Status quo (`BackdropFilter` + `GlassPainter`) | No | Yes | Known, tested |

**Flutter offers no native option.** Tracking issue #170310 is still open at P3 with no assignee. Since August 2026 it lives in the new standalone `cupertino_ui` package ([GitHub #170310](https://github.com/flutter/flutter/issues/170310)). The decoupling post says "work is already underway on official implementations of Liquid Glass" but gives no date, and it does not say native or drawn ([Flutter blog](https://flutter.dev/blog/decoupling-material-cupertino)). The only concrete upstream work is two pending flutter/packages PRs (#13162, #13163) that vendor the shader-based `liquid_glass_renderer` ([GitHub #170310](https://github.com/flutter/flutter/issues/170310)). The official answer is converging on imitation glass, which is close to what Hearthrise already paints.

The first route is the only one that meets the brief. On iOS, platform views always use hybrid composition: the real `UIView` sits in the UIKit hierarchy ([Flutter docs](https://docs.flutter.dev/platform-integration/ios/platform-views)). Flutter content painted *before* the platform view lands in the base FlutterView Metal layer behind it, where the system backdrop sampler can read it. Content painted *after* it goes into overlay layers on top. The glass cannot refract those layers, but they do sit visibly over the glass, and that is exactly where the ink layer belongs. `fresnel` uses this architecture: SwiftUI `.glassEffect()` in a `UIHostingController` hosted in a `UiKitView`, with "content [as] an ordinary Flutter subtree composited above it." On an iPhone 17 Pro **simulator** running iOS 26.1, it reports that "native SwiftUI glass samples and refracts Flutter-rendered content beneath it" ([pub.dev fresnel](https://pub.dev/packages/fresnel)). **That is the only evidence, and it is simulator-only.** One search snippet attributed to `ios_liquid_glass` claimed the opposite, while that package's own page agrees with fresnel ([pub.dev ios_liquid_glass](https://pub.dev/packages/ios_liquid_glass)). Apple documents nothing about glass sampling `CAMetalLayer` content. The pre-glass precedent is encouraging: `UIVisualEffectView` blurs do work over a `CAMetalLayer` ([Apple Developer Forums 62286](https://developer.apple.com/forums/thread/62286)).

Three structural limits follow, and the first hits Hearthrise hardest. **First, `fresnel` reports that any Flutter `BackdropFilter` in the same scene "makes the platform view stop rendering entirely"**, with no error and no known cause ([pub.dev fresnel](https://pub.dev/packages/fresnel)). Every `GlassSurface` today runs a backdrop blur. On a route that shows native glass, every remaining Flutter glass surface must run with `blur: 0`, the parameter `GlassSurface` already has for glass over a known fill. Otherwise the whole route must stay on one path. Second, a Flutter clip "becomes a mask on the glass view's parent", and Flutter cannot fade the glass ([pub.dev ios_liquid_glass](https://pub.dev/packages/ios_liquid_glass)). Apple forum guidance says a masked superview breaks backdrop sampling, so the mask has to sit on the effect view itself ([Apple Developer Forums 50854](https://developer.apple.com/forums/thread/50854)). The shape must therefore travel over the channel as `cornerConfiguration`, never as a Flutter `ClipPath`. Third, packages report z-order bugs. Native glass halos bleed through Flutter sheets, and native bars render above modal content unless a route observer hides them ([GitHub cupertino_native_better](https://github.com/gunumdogdu/cupertino_native_better)). `native_liquid_glass` hides glass during route pushes because Flutter's surface "may not be readable" mid-transition ([pub.dev native_liquid_glass](https://pub.dev/packages/native_liquid_glass)). Sheets and alerts, which `GlassSurface` also draws, should stay on the Flutter path.

A shader upgrade remains the low-risk alternative for the fallback and for scrolling content. Flutter 3.29 added `BackdropGroup` and an `ImageFilter.shader` that works as a backdrop filter. Both are Impeller-only and throw on other backends ([What's new in Flutter 3.29](https://flutter.dev/blog/whats-new-in-flutter-3-29); [Flutter docs](https://docs.flutter.dev/ui/design/graphics/fragment-shaders.md)). Adding a refraction shader to `GlassSurface`'s existing blur gets most of the look with no dependency and no platform views. It still lacks Apple's adaptive tint, morphing and system accessibility.

## The ink layer must do its own accessibility work

The system applies three accessibility settings to native glass automatically. Reduce Transparency makes it "frostier". Increase Contrast makes elements "predominantly black or white" with "a contrasting border". Reduce Motion "disables any elastic properties" ([WWDC25 219](https://developer.apple.com/videos/play/wwdc2025/219/)). The iOS 26.1 **Clear/Tinted** preference also applies to third-party glass ([Macworld](https://www.macworld.com/article/2947565/ios-26-1-beta-4-does-the-unthinkable-you-can-control-how-glassy-liquid-glass-should-be.html); [Tom's Guide](https://www.tomsguide.com/phones/iphones/ios-26-1-lets-you-adjust-liquid-glass-transparency-on-your-iphone-heres-how-to-do-it)). None of this reaches Flutter-drawn content. Native labels inside `contentView` "automatically become vibrant" ([WWDC25 284](https://developer.apple.com/videos/play/wwdc2025/284/)), but the ink sits outside it. And the native view "doesn't report what it samples" ([pub.dev ios_liquid_glass](https://pub.dev/packages/ios_liquid_glass)).

Flutter reports some of these settings and misses others. It exposes Increase Contrast as `MediaQuery.highContrast` (from `UIAccessibilityDarkerSystemColorsEnabled`) and exposes Reduce Motion. **It has no Reduce Transparency field** ([AccessibilityFeatures](https://api.flutter.dev/flutter/dart-ui/AccessibilityFeatures-class.html); [engine source](https://raw.githubusercontent.com/flutter/flutter/master/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterViewController.mm)). No public API for Clear/Tinted turned up. Hearthrise therefore needs three things. First, a small event channel for `UIAccessibility.isReduceTransparencyEnabled` and its change notification; that is standard UIKit, not re-verified in this research. When it fires, drop the glint and lit rim, because they imply a translucency the system has removed. Second, a rule for high contrast. `GlassSurface` already swaps blur and sheen for a flat shell fill under high contrast. On the native path the system adds its own border, so thin or drop the ink key line there rather than drawing a double outline. Third, an overlay that reads over both Clear and Tinted, since the app cannot tell which is active. Legibility is the deeper issue. Small glass flips dark over dark scenes, which can swallow a dark ink line. Apple's guidance allows content on glass only as "a thin overlay that is part of the material", and says a solid fill "breaks the visual character of Liquid Glass" ([WWDC25 219](https://developer.apple.com/videos/play/wwdc2025/219/)). Keep the key line thin and partly transparent, give the ink a light halo, and test over Hearthrise's darkest biome.

Press response is a separate choice. `isInteractive` / `.interactive()` adds the system scale, bounce and shimmer, but only for touches the native view receives ([WWDC25 323](https://developer.apple.com/videos/play/wwdc2025/323/)). `fresnel` keeps the native view non-interactive with transparent hit testing and sends a `setPressed` message from Flutter's gesture arena ([pub.dev fresnel_ios](https://pub.dev/packages/fresnel_ios)). `ios_liquid_glass` dropped native press response entirely because it never fired ([pub.dev ios_liquid_glass](https://pub.dev/packages/ios_liquid_glass)). Apple documents no way to trigger the press state without a real touch. The simplest course keeps gestures and semantics in Flutter and drives `GlassSurface.isPressed` as today. It also turns off Flutter's own bounce under Reduce Motion, to match the system.

## Performance caps native glass at a handful of surfaces

Apple publishes no numbers. It says only that "too many Liquid Glass effect containers and... effects to views outside of containers can degrade performance", and that grouping in a container gives "the best rendering performance" ([Apple](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)). Glass also "can not sample other glass", so neighbouring glass in separate containers behaves inconsistently ([WWDC25 323](https://developer.apple.com/videos/play/wwdc2025/323/)). Flutter adds its own costs on top. Each platform view splits the layer tree, and Flutter content painted over a platform view forces an extra overlay surface. Package authors advise **one or two platform views per screen** and measuring in release builds ([pub.dev native_liquid_glass](https://pub.dev/packages/native_liquid_glass)). `LiquidGlassContainer` inside long lists "will cause significant performance drops (jank)" ([pub.dev cupertino_native_better](https://pub.dev/packages/cupertino_native_better)). Grouping all of a screen's glass shapes under one `UIGlassContainerEffect` in one platform view, as `real_liquid_glass`'s `LiquidGlassGroup` does, makes N shapes cost one view ([pub.dev real_liquid_glass](https://pub.dev/packages/real_liquid_glass)). The engine adds a separate risk. flutter/flutter #190815 reports jank on iOS whenever *any* platform view is visible, caused by the merged platform/UI thread. Build and raster times look healthy throughout, and the reported workaround is `FLTEnableMergedPlatformUIThread = false` in Info.plist ([GitHub #190815](https://github.com/flutter/flutter/issues/190815)). On older iPhones, glass reportedly causes lag, but those reports are anecdotal ([MacObserver](https://macobserver.com/tips/round-ups/i-tested-ios-26-on-iphone-se-with-liquid-glass-and-it-feels-laggy)).

The shader alternative has its own budget, and Hearthrise already pays part of it. On Impeller each independent backdrop layer copies the render pass ([pub.dev liquid_glass_renderer](https://pub.dev/packages/liquid_glass_renderer)). `liquid_glass_widgets` reports that one shared backdrop read cut GPU time from 23.6 ms to 9.3 ms per frame on an iPhone Air in one sheet-over-bars case, a publisher figure from one scene ([pub.dev liquid_glass_widgets](https://pub.dev/packages/liquid_glass_widgets)). Wrapping sibling `GlassSurface`s in `BackdropGroup` is worth doing whether or not native glass ships.

## Conclusion

The real decision is not native versus drawn. It is which surfaces earn native glass. On iOS 26+, native glass is worth its compositing cost only for the persistent tab bar and header circles. There, adaptive tint, Apple's accessibility handling and the Clear/Tinted preference come free. Sheets, alerts, pills and the switch stay on the Flutter path. The `BackdropFilter` conflict forces one more rule: within a route, glass is either all native (with Flutter glass at `blur: 0`) or all Flutter. `GlassSurface` already separates material from ink and already has a `blur: 0` mode, so the change is a new bottom layer rather than a rewrite. The gate and the per-setting overlay rules are unit- and widget-testable. Refraction of Flutter pixels, BackdropFilter suppression, halo bleed and frame time are not, and they go in the plan as manual device checks.

Two unknowns should be settled before any production code is written. The first is whether native glass refracts Flutter's Metal layer on a real device; all current evidence comes from one simulator run. The second is whether #190815's jank shows on Hearthrise's screens. A one-day spike answers both: one material-only `UIVisualEffectView` under the tab bar, on a physical iOS 26 phone, in a release build. If either fails, upgrade the existing painter with an Impeller refraction shader and `BackdropGroup` instead. That is also where Flutter's own Liquid Glass work appears to be heading.
